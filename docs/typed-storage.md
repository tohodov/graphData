# Типизированный граф и представления хранения

По умолчанию API использует `GraphStorage:Mode = legacy` и прежний каталог
`GraphStorage:RootPath` (`E:\TTT\weapon` в текущей конфигурации). Старый редактор
и MCP продолжают работать в этом режиме. Новый типизированный API доступен
поверх того же хранилища через адаптер; перенос файлов для этого не нужен.

## Граница контракта

[`ITypedGraph`](../TypedGraph/Contracts.cs) — публичная предметная модель:
определения типов, экземпляры, отношения, атрибуты и именованные участники.
[`TypedGraphService`](../TypedGraph/TypedGraphService.cs) проверяет общие правила,
замыкание требований типов, кардинальности и значения скалярных атрибутов.
Чтения возвращают отдельные снимки, без активных объектов хранилища.

`ITypedGraphStore` — точка расширения для реализаций хранения. Это технический
порт для `TypedGraphService`, а не альтернативный клиентский граф. Его
реализации обязаны явно отклонять повреждённые и непредставимые данные.

```text
HTTP /api/typed-graph → ITypedGraph / TypedGraphService
                              ↓ ITypedGraphStore
                ┌─────────────┴────────────────┐
       CarrierTypedGraphStore          SemanticRecordStore
       прежний recursive graph         канонические JSON-записи
       IGraphStorage / symlinks        отдельный native-каталог
```

Рекурсивный слой обозначается именами `CarrierGraph`, `CarrierNode`,
`CarrierEdge`, `CarrierGraphService`, `CarrierSubgraph`, `CarrierNodeBacking`
и `CarrierEdgeBacking`. Это представление хранения и совместимость,
не типы публичного `ITypedGraph`. Native backend использует отдельные классы
и не реализует `IGraphStorage`; `NodeBacking`-фасада и вычисляемого raw-графа
у него нет.

У `TypedElement` есть `Id`, `Kind`, `TypeIds`, `Attributes` и `Members`.
`TypeIds` содержит материализованные эффективные типы, включая необходимые
типы. Это не история назначений: различие между явно назначенным типом
и типом, полученным через требования, контракт не обещает восстановить.

`Members` — словарь «имя роли → множество ID участников» без значимого порядка.
Роль задаёт допустимый тип и кардинальность. Участниками могут быть экземпляры
и другие отношения. Отношение имеет собственный ID; несколько отношений
между теми же участниками не сливаются в одно ребро. Используется выбранный
по умолчанию каталог типов, без клиентского параметра интерпретации `basis`.

## Доступные операции

Все адреса ниже относятся к `/api/typed-graph`.

| Операция | HTTP |
|---|---|
| Каталог типов | `GET /types` |
| Определение типа | `GET /types/item?id=…` |
| Создание типа | `POST /types` |
| Чтение экземпляра или отношения | `GET /elements?id=…` |
| Отношения, в которых участвует элемент | `GET /relations/incident?participantId=…` |
| Создание экземпляра | `POST /instances` |
| Создание отношения с именованными ролями | `POST /relations` |
| Полная замена атрибутов элемента | `PUT /elements/attributes?id=…` |
| Удаление элемента | `DELETE /elements?id=…` |

Удаление работает по правилу restrict: сначала требуется явно удалить
ссылающиеся отношения. Carrier-адаптер также отклоняет удаление, которое
затронуло бы не представленные в контракте дочерние узлы или связи.
ID используются в каноническом написании, без нормализации и угадывания
алиасов. Создание не перезаписывает существующую запись; коллизии регистра
идентификаторов отклоняются.

Carrier-адаптер до записи проверяет также локальные имена всех планируемых
связей и обратных ссылок. Например, разные участники `a/same` и `b/same`
могут не помещаться в одну роль старого формата: такой запрос получает
`Unsupported`, не оставляя частично созданного отношения.
Расхождение сохранённой схемы с кешем или CLR-описанием считается `Corrupt`.
Повторяющиеся JSON-поля и недопустимые `null` в HTTP-запросах отклоняются
до вызова операций графа.

Текущий общий контракт ограничен:

- новые экземпляры и отношения создаются с одним локальным сегментом ID;
  новые типы — непосредственно как `NodeTypes/<name>`;
- именованные node-valued поля экземпляров пока не поддержаны: для именованной
  связи нужен отдельный тип отношения;
- у отношения одна схема с минимум двумя именованными ролями; наследование
  и объединение нескольких схем отношений не определены;
- изменение или удаление схемы типа, переназначение типов, изменение состава
  участников отношения, typed-поиск и общий typed-subgraph пока не выставлены;
- выбор другого type scope через этот контракт не предоставляется.

Ошибки явные: `Invalid` → HTTP 400, `NotFound` → 404, `Conflict` → 409,
`Unsupported` → 501, `Corrupt` → 500. Непредставимая старая конструкция
не превращается в догадку о типах или успешный пустой результат.

## Включение native-хранилища

Пример конфигурации API:

```json
{
  "GraphStorage": {
    "Mode": "semantic",
    "RootPath": "E:\\TTT\\weapon"
  },
  "SemanticGraphStorage": {
    "RootPath": "E:\\TTT\\weapon-native-typed"
  }
}
```

Native root задаётся отдельно и не должен совпадать с legacy root, находиться
внутри него или содержать его. Новый пустой каталог инициализируется своим
маркером. Автоматического импорта или ремонта нет. Прежний эксперимент
`60c396e` тоже имеет другой формат: его каталоги `types/instances/indexes`
не являются текущим native-хранилищем и требуют явной миграции.

В `semantic` сейчас доступен **только типизированный HTTP API**. Старые
`/api/graph`, `/api/ui` и главная страница редактора отвечают явным 501.
Текущий MCP при `Mode = semantic` отказывает при запуске с объяснением;
его профиль инструментов `Semantic` не означает поддержку native backend.
Для прежнего UI и MCP нужен `Mode = legacy`.

## Формат native и согласованность

```text
<root>/
  typed-graph-store.json           format: graphdata-native-typed-records, version 1
  .typed-graph-store.lock          эксклюзивная блокировка открытого backend
  types/<sha256-utf8-id>.json      definition типа
  instances/<sha256-utf8-id>.json  экземпляр или отношение
```

Каждый файл записи содержит `formatVersion`, `recordKind` и `value`.
Имя файла вычисляется из полного ID; ID также хранится в документе и
проверяется при чтении. Хэширование не меняет предметную идентичность.
Адреса не создают отношений или каскадного владения по префиксу.
Неизвестная версия, неверный kind, повторяющиеся JSON-поля, несогласованный
ID и некорректная структура отклоняются как повреждение.

Один открытый `SemanticRecordStore` удерживает exclusive lease на root.
Второй backend для этого каталога, в том числе в другом процессе, получает
отказ; `Dispose` освобождает блокировку. Записи заменяются атомарно через
временный файл. Это атомарность одного документа, не транзакция нескольких
документов или всего графа.

Обратный поиск участников пока детерминированно сканирует записи экземпляров;
проверка коллизий при создании также читает канонические коллекции.
Производных incidence-индексов в текущем native backend нет, поэтому эти
операции имеют стоимость обхода записей.

Legacy-операции могут изменять несколько файлов и симлинков. Общая
сериализация вызовов `TypedGraphService` не делает их crash-safe транзакциями
и не синхронизирует отдельные процессы или старые raw-записи. Прежние raw API,
UI и MCP остаются отдельной границей совместимости; их физические связи
не становятся частью публичного типизированного контракта.
