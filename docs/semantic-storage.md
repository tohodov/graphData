# Экспериментальное семантическое хранилище

Эта ветка проверяет одну архитектурную гипотезу: наблюдаемость должна быть свойством канонической записи на диске, а не результатом распознавания семантики в реифицированном простом графе.

## Главные инварианты

1. Каталог типов и граф инстансов — разные пространства хранения.
2. Каталог типов организован как дерево. Путь типа одновременно задаёт его устойчивый идентификатор и положение в каталоге.
3. Инстансы образуют граф. Сегменты их `GlobalId` — только пространство имён и локатор файла; они не создают semantic edge, containment или каскадное владение.
4. Типизация инстанса хранится рядом с самим инстансом как список слабых `TypeRef`. Отсутствующий тип не делает запись инстанса нечитаемой и не стирает исходный идентификатор типа.
5. Отношение — самостоятельная каноническая запись с именованными членами и списками участников. Бинарные, n-арные, параллельные и higher-order отношения используют один формат.
6. Участниками отношения могут быть инстансы и другие отношения. Типы не входят в instance-граф; ссылки на них существуют только в метаинформации.
7. Индекс инцидентности производный. Он ускоряет локальный переход «инстанс → связанные отношения», но не является вторым источником истины.
8. Правила отображения принадлежат типам. Изменяемого набора узлов, который заново объявляет, что считать типами, больше нет.
9. Зависимости higher-order отношений образуют DAG: отношение не может прямо или транзитивно содержать само себя как участника.
10. У relation ровно один конкретный Edge-классификатор. Повторное назначение того же типа идемпотентно; смена схемы выполняется явной заменой relation record.

```text
types/                         instances/
  .../type.json                  .../instance.json
       |                              |  typeIds: [...]
       | weak TypeRef                 |
       +------------------------------+

instances/<relation>/instance.json
  kind: relation
  typeIds: [...]
  members:
    - name: Source
      participantIds: [...]
    - name: Targets
      participantIds: [...]
```

## Физическая схема

```text
<root>/
  types/
    Weapon/
      type.json
      Pistol/
        type.json
  instances/
    arsenal/
      glock-17/
        instance.json
    shipment-42/
      instance.json
  indexes/
    incidents/
      arsenal/
        glock-17/
          relations.json
```

Запись обычного инстанса:

```json
{
  "formatVersion": 1,
  "id": "arsenal/glock-17",
  "kind": "instance",
  "typeIds": ["NodeTypes/Pistol"],
  "attributes": {
    "label": "Glock 17"
  },
  "members": []
}
```

Запись отношения:

```json
{
  "formatVersion": 1,
  "id": "shipment-42",
  "kind": "relation",
  "typeIds": ["NodeTypes/Shipment"],
  "attributes": {},
  "members": [
    {
      "name": "Source",
      "memberTypeId": "NodeTypes/Shipment/Definition/Slots/Source",
      "participantIds": ["warehouse-a"]
    },
    {
      "name": "Cargo",
      "memberTypeId": "NodeTypes/Shipment/Definition/Slots/Cargo",
      "participantIds": ["arsenal/glock-17", "arsenal/glock-19"]
    }
  ]
}
```

Одна запись отношения локально отвечает на вопросы «что это за отношение», «какие роли в нём есть» и «кто участвует». Для обратного вопроса «в каких отношениях участвует этот элемент» читается один производный incidence-файл. Исправление отношения меняет его документ и только индексы затронутых участников.

## Что означает наблюдаемость в этой ветке

| Вопрос | Ограниченная область чтения | Точечное исправление |
|---|---|---|
| Что хранит инстанс? | один `instance.json` | один документ |
| Какие типы объявлены у инстанса? | поле `typeIds` того же документа | тот же документ |
| Как устроено отношение? | один relation document | один relation document и индексы его участников |
| Какие отношения затрагивают инстанс? | один incidence document, затем выбранные relation documents | исправляется конкретное отношение |
| Как описан тип? | локальное поддерево типа | запись типа или конкретный элемент его определения |
| Как элемент отображается? | display-атрибуты его типа | запись типа |

Это не обещание, что любой вопрос имеет стоимость `O(1)`. Транзитивное замыкание требований типов или обход связной компоненты по определению затрагивает несколько локальных записей. Инвариант слабее и практичнее: стоимость чтения определяется самим вопросом, а не необходимостью сначала распознать глобальную carrier-грамматику.

Для стартового frontier UI storage умеет отдельно перечислить ближайшие канонические записи под заданным namespace-prefix. Пустые промежуточные каталоги при этом прозрачны. Результаты такого listing становятся независимыми корнями представления и не добавляют рёбер между prefix и найденными элементами.

Полная загрузка дерева типов — отдельная операция `GET /api/graph/type-catalog`. Она перечисляет только `types/` и не обходит instance graph. Поэтому глубина дерева типов не ограничена UI-константой, а явная глобальная стоимость возникает только при запросе всего каталога.

### Named node fields

`NodeFieldDefinition` и `NodeSlotDefinition` пока описывают схему, но для node-valued field assignment в этом эксперименте ещё не выбран отдельный канонический record. До выбора формата система ведёт себя fail-fast и не восстанавливает имя поля из топологии:

- Semantic MCP отклоняет переданное node-valued поле до создания инстанса;
- `AssignNodeTypeAsync` отклоняет Node type с обязательным таким member;
- необязательный отсутствующий member считается пустым;
- raw relation и подходящий тип её второго участника не удовлетворяют slot и не превращаются UI в значение поля.

Если связь нужна сейчас, её следует объявить как Edge type с явными именованными members и создать через `CreateRelation`. Это сохраняет один наблюдаемый relation document и не вводит временную carrier-грамматику, которую позднее пришлось бы распознавать и мигрировать.

## Согласованность и восстановление

- Записи JSON заменяются атомарно через временный файл. Создание, замена и удаление элементов type tree сериализованы одним gate, поэтому параллельное создание потомка не может оставить orphan после удаления родителя.
- `TypeRef`, `requiredTypeIds` реального типа и `memberTypeId` являются слабыми ссылками. Их цель может временно отсутствовать. Служебные элементы определения типа не имеют собственных `requiredTypeIds`.
- `participantIds` проверяются при создании отношения: участник должен существовать в instance-графе.
- При создании или замене higher-order отношения storage запускает локальный DFS от его участников-отношений по их `participantIds`. Если обход достигает идентификатора создаваемого или заменяемого отношения, изменение отклоняется. Проверяется только затронутое замыкание зависимостей, без глобального обхода instance-графа.
- Удаление инстанса удаляет только этот инстанс и отношения, которые непосредственно на него ссылаются. Потомки по префиксу идентификатора не удаляются.
- У каждого инстанса и relation есть incidence-маркер, включая элементы с нулевой степенью. Отсутствующий маркер не интерпретируется как «связей нет»: потенциально разрушительная мутация останавливается с требованием явного repair.
- Incidence index обновляется по затронутым участникам. Полное восстановление из канонических relation documents запускается явно через repair и не выполняется при обычном открытии, чтении или мутации.
- Материализация runtime-определения типа помечается завершённой только после записи `Definition`, `Fields` и `Slots`. После прерывания следующий `OpenAsync` продолжает незавершённую запись идемпотентно.
- Backup читает каждую каноническую запись одним атомарным snapshot, сохраняет только semantic records и перед восстановлением валидирует весь план, включая физические case-collision. Compatibility projection и индексы восстанавливаются из каноники.

## Граница совместимости

`Domain` всё ещё использует исторический `IGraphStorage` для части API. Новое хранилище реализует его как вычисляемую проекцию:

- type tree проецируется как навигационные связи каталога;
- слабый `TypeRef` может проецироваться как связь к типу;
- typed relation может проецироваться как relation/member/participant узлы для старых потребителей;
- простая нетипизированная связь хранится как скрытая relation record и проецируется прямым ребром.

Эти узлы и рёбра не записываются вторым графом и не участвуют в определении канонической семантики. Новые функции должны читать `ISemanticGraphStorage`, `SemanticKind`, `TypeIds` и `RelationMembers`, а не распознавать форму compatibility projection.

Автоматической миграции старых `node.json`/symlink-данных в этой ветке нет: смешивать две схемы в одном каталоге было бы неоднозначно. Поэтому конфигурации API и MCP по умолчанию указывают на новые semantic roots; прежнее хранилище остаётся нетронутым и может быть перенесено отдельным проверяемым импортом.

Точечное изменение relation document и нескольких incidence documents пока не объединено файловой транзакцией. После аварийного завершения между этими записями может потребоваться явный repair производного индекса; это осознанное ограничение эксперимента, а не скрытый глобальный scan при каждом запуске.

Два ограничения масштабирования оставлены явными: автоматически создаваемые compatibility-relations пока получают GUID-идентификаторы в корневом instance namespace, а `refreshTypes` читает весь каталог типов без paging. Здесь нет логической зависимости графа от дерева адресов, поэтому последующее шардирование relation-файлов и ленивую загрузку type rules можно добавить без изменения semantic model.

## Критерий результата эксперимента

Гипотеза считается полезной, если реальные сценарии удаётся реализовывать через ограниченные чтения и исправления перечисленных документов без нового глобального соглашения о carrier-подграфах. Если для каждого нового доменного свойства снова потребуется распределённая грамматика и глобальная проекция, перенос семантики в storage не решил исходную проблему.
