# graphData

graphData — исследовательский прототип семантического графового хранилища для локально наблюдаемых и инкрементально изменяемых структур.

Основная прикладная цель — динамический MCP/RAG для программных и нейросетевых агентов. Более дальняя цель — хранить сложные модели так, чтобы отдельный фрагмент можно было прочитать, проверить и исправить без загрузки или понимания всей системы.

Эта экспериментальная ветка заменяет прежнюю основу из реифицированного простого графа. Канонической записью на диске теперь является типизированный семантический граф.

## Модель

Хранилище разделено на две части:

- дерево типов — локальный каталог определений и display rules;
- граф инстансов — обычные инстансы и самостоятельные relation records.

У инстанса список идентификаторов типов лежит в его собственном `instance.json`. Это слабые ссылки: отсутствующий или временно недоступный тип не мешает прочитать и исправить инстанс.

Отношение хранит свой тип и все именованные роли с участниками в одном документе. Один формат покрывает бинарные, n-арные, параллельные и higher-order отношения. Участниками могут быть инстансы и другие отношения; type tree не смешивается с instance graph.

```text
type tree                       instance graph
types/**/type.json              instances/**/instance.json
       ^                              |
       | weak TypeRef                 | named relation members
       +------------------------------+

derived locality index
indexes/incidents/**/relations.json
```

Подробная схема, примеры JSON, границы согласованности и критерий проверки гипотезы описаны в [docs/semantic-storage.md](docs/semantic-storage.md).

## Наблюдаемость

В проекте наблюдаемость означает:

- локализацию связанной информации;
- ограниченное и предсказуемое чтение;
- простой контроль количества и качества найденных элементов;
- точечное исправление без переписывания несвязанной части графа.

Путь инстанса — только идентификатор и файловый локатор. Он не создаёт скрытое semantic edge, containment или каскадное владение. Связность instance graph задаётся только relation records. Обратный переход от участника к отношениям выполняется через производный локальный incidence index.

## Проекция и совместимость

`ISemanticGraphStorage` — источник истины. Старый `IGraphStorage` пока сохраняется как вычисляемая compatibility projection для существующих частей Domain, API и UI. Виртуальные relation-member узлы и простые рёбра этой проекции не записываются на диск и не должны использоваться для распознавания семантики.

Изменяемого projection basis больше нет. Каталог типов фиксирован хранилищем, а отображение задаётся правилами конкретного типа: видимостью, цветом, рангом, сворачиванием, направленностью и подписью.

## Проекты

- `Abstractions` — внутренние storage-контракты, backing-состояния и идентификаторы.
- `SemanticStorage` — файловое каноническое хранилище типов, инстансов, отношений и производных индексов.
- `Domain` — активные `Node`/`Edge`, type DSL и `GraphService`.
- `Api` — HTTP API и web UI.
- `Mcp` — раздельные semantic/raw MCP-профили.
- `Compiler` — lowering конечного graph snapshot в dense/CSR IR и HLSL.
- `Runtime` — Direct3D 12 execution runtime.

Исполняемые входы работают через `GraphService`. Новая функциональность, которой нужен смысл элемента, должна читать `SemanticKind`, `TypeIds` и `RelationMembers`, а не форму compatibility graph.

## Attributes policy

`Attributes` остаются пользовательскими данными и escape hatch для импорта, подписей и display rules. Строковые convention-атрибуты не должны определять, является ли элемент типом, инстансом или отношением: это часть storage record.

Техническая граница проверяется `AttributePolicyTests`: Domain может пробрасывать пользовательские attributes и искать по ним, но не должен кодировать внутреннюю типовую семантику строковыми marker-ключами.

## API и MCP

HTTP `NodeResponse` сообщает:

- `semanticKind`;
- объявленные `typeIds`;
- канонические `relationMembers`;
- compatibility edges для ленивой навигации старых клиентов.

`POST /api/graph/relations` создаёт типизированное отношение с именованными наборами участников.

Semantic MCP предоставляет операции над типами, типизированными узлами и отношениями. Raw MCP сохранён как явно низкоуровневый диагностический профиль; он не выдаётся за семантическую модель.

Node-valued fields в описании Node type пока являются только схемой: канонический формат их assignment ещё не выбран. Поэтому обязательные named fields отклоняются до мутации, optional field может быть только пустым, а raw-связь не считается значением поля. Рабочая явная форма связи в этой ветке — Edge type плюс `CreateRelation`.

## Web UI

UI загружает граф по frontier, а не целиком. `NodeResponse.edges` позволяет показать ещё не загруженных соседей, после чего пользователь раскрывает нужное продолжение.

Каталог типов запрашивается отдельно через `GET /api/graph/type-catalog`: операция перечисляет только type tree, поддерживает произвольную глубину и не сканирует инстансы.

Типизация и relation records приходят непосредственно с backend. Вкладка типов управляет только правилами отображения по type id. Для n-арного отношения UI может оставить relation node видимым; бинарное отношение при включённом сворачивании отображается обычным ребром.

## Backup

Backup version 2 сохраняет только канонические type, instance и relation records. Compatibility projection и incidence index не сериализуются как второй источник истины и восстанавливаются из semantic records.

## Проверка

Основные тестовые сборки:

- `DomainTests` — storage contracts, semantic typing, relations, backup/search и Domain;
- `ApiTests` — HTTP и UI;
- `McpTests` — semantic/raw tool surfaces;
- `CompilerTests` и `RuntimeTests` — компилятор и runtime;
- `PerformanceTests` — измерительные сценарии.

```powershell
dotnet test Tests/DomainTests/DomainTests.csproj
dotnet test Tests/ApiTests/ApiTests.csproj
dotnet test Tests/McpTests/McpTests.csproj
dotnet build GraphData.slnx
```

При запуске через PowerShell на Windows файлы с русским текстом следует читать с явным `-Encoding UTF8`.
